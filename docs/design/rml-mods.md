# RML・Mod管理（初期版仕様）

2026-10-17 合意。本書を初期版の機能範囲の正本とする。

## 1. 方針

- Web UIの「Mod」タブから、RMLとRML向けModのDLLを管理する。
- Mod構成はMRHCが管理するヘッドレス全体で共通。
- 閲覧と更新確認は稼働中も可能。導入・更新・有効／無効・削除・復元は**停止中のみ**。
- 変更はその場で保存し、次回のヘッドレス起動で使用する。
- 更新確認・ダウンロード・更新適用はユーザー操作で行う。
- 既存の認証・画面部品・日本語／英語対応を使用する。

## 2. 画面と操作

「Mod」タブにはRML欄とMod一覧を置く。

| 対象 | 表示 | 操作 |
|---|---|---|
| RML | 未導入／導入済み、有効／無効、導入版、更新確認結果 | 導入、更新確認、更新、有効／無効、更新前へ戻す |
| Mod | ファイル名、有効／無効、入手元、導入版または登録日時、更新確認結果 | 追加、差し替え、更新確認、更新、有効／無効、削除、更新前へ戻す、GitHub更新元の登録 |

- RMLは公式配布元 `resonite-modding-group/ResoniteModLoader` から取得する。必要なHarmonyもRML側でまとめて管理する。
- Mod追加の入口は「DLLをアップロード」「GitHubから追加」の2つ。
- RML全体を無効にしても、各Modの有効／無効は保持する。RMLを有効に戻すとその構成を使用する。
- 個別Modを無効にしてもDLLを保持し、RMLの読み込み対象から外す。
- Mod削除は当該ModのDLL・管理情報・復元用DLLを対象とし、Mod設定ファイルは残す。
- 導入・差し替え・更新・無効化ではMod設定ファイルを保持する。
- 「導入済み」「有効」は配置・設定の状態を表す。
- 停止が必要な操作にはその条件を表示する。削除確認は既存UIの方式に合わせる。

## 3. DLLの追加と更新

### アップロード

- DLLのみ受け付ける。
- 新規追加と既存Modの差し替えを区別する。同名ファイルを新規追加しても、既存Modを黙って上書きしない。
- 版が不明なものはファイル名・登録日時で識別する。
- アップロードしたModにも、後からGitHubの更新元と対象DLLを登録できる。

### GitHub

1. 公開GitHubリポジトリのURLを入力する。
2. リリースを選ぶ。既定は最新の正式リリースとし、過去の正式リリースも選択できる。
3. そのリリースに添付されたDLLを選び、取得する。

- GitHub Releasesの添付DLLを扱う。
- リポジトリ、取得したリリース、選択したDLLを記録し、以後の更新確認に使う。
- GitHub経由で取得した版はリリースタグで表示する。更新元の登録だけでは、手元のDLLがその版だと見なさない。
- 更新時も対象DLLだけを取得する。対象を特定できない場合は再選択を求める。
- 更新確認の失敗は「確認失敗」と表示する。「更新なし」とは区別し、既存ファイルを変更しない。

## 4. 適用と復元

- ダウンロード／アップロードしたファイルを検査してから既存DLLと差し替える。
- 更新前のDLLと、その版・入手元の記録を**1世代**保存する。「更新前へ戻す」はそれらを復元する。初回追加には復元先がない。
- RMLと同時に管理するHarmonyは、更新・復元を同じ単位で扱う。
- 取得・検査・適用に失敗した場合は、変更前の構成を維持または復元し、エラーを表示する。
- 復元対象は管理しているDLLと管理情報のみ。
- 起動失敗からの切り分けは、利用者が停止中に個別ModまたはRML全体を無効にして行う。

## 5. 実装上の最低条件

- 停止条件はUIだけでなくサーバー側で確認する。起動中・停止処理中・再起動処理中も変更不可。
- ファイル変更は、すべての起動経路（手動・予定・クラッシュ復帰）およびResonite本体の更新と競合させない。処理開始前に排他し、同時操作は受け付けない。
- 認証済みの管理操作として扱う。ファイル名・保存先・DLL形式・受信サイズを検査し、管理対象外のパスへの書き込みを許可しない。検査のためにDLLを実行しない。
- GitHub取得は対象リポジトリのRelease添付ファイルに限定する。
- 管理情報と実際のファイルを一致させる。適用中断で不整合が残った場合は、混在した構成でヘッドレスを起動せず、エラーを表示する。
- 手動配置された既存DLLを黙って上書き・削除・管理下へ取り込みしない。配置先が競合したら処理を止めて対象を知らせる。
- RMLが無効ならRMLの起動指定を付けない。有効時の指定は手動起動・予定再起動・クラッシュ復帰で共通にする。
- 既存のテスト方式を使い、停止条件と起動競合、ON/OFF、更新失敗時の維持、1世代復元、不正な入力の拒否を最小限の実行可能な検査で確認する。

## 6. 配置と保存

- 公式の同じ正式リリースにある `ResoniteModLoader.dll` と `0Harmony.dll` を組にする。2026-10-17に5.0.1の配布物と公式ソースを確認。Windows／Linux x64／Linux ARM64とも同じマネージドDLLを使用する。実機での各OS動作確認は別途行う。
- 作業ディレクトリ `Headless/` を基準に、RMLを `Libraries/ResoniteModLoader.dll`、Harmonyを `rml_libs/0Harmony.dll`、有効Modを `rml_mods/<ファイル名>` に配置する。RML有効時だけ `-LoadAssembly Libraries/ResoniteModLoader.dll` を付ける。
- `Headless/.mrhc-mods/state.json` にRML・Modの有効状態、現在版と前版（ファイル名、SHA-256、登録日時、取得元・タグ・asset名）を保存する。既存 `mrhc.config.json` の形式は変更しない。インストール先を変更すると、その先のMod構成を使用する。
- DLL原本は `.mrhc-mods/blobs/<SHA-256>.dll` に置く。無効Modは原本だけを保持する。現在版・前版から参照されない原本は削除する。
- インストール先の変更も停止中・他処理なしの場合に受け付ける。前版にはその時点のGitHub更新元も含め、復元時に戻す。
- 適用前に旧・新構成のジャーナルを保存し、DLL配置とstate保存が完了したら削除する。途中失敗は旧構成へ戻す。中断後は次の管理操作／起動前に旧構成へ復旧し、復旧できない場合は起動を止める。
- DLLは1ファイル32 MiBまで。.NETのPE/CLIヘッダーを検査する。ファイル名は単一のDLL名に限定し、OSの予約名・パス指定を拒否する。LinuxのRMLで認識できるよう配置時の拡張子を `.dll` に揃える。配置先で大文字小文字だけ異なる名前も衝突として扱う。

根拠：[公式導入手順](https://github.com/resonite-modding-group/ResoniteModLoader/blob/main/README.md)、[読み込みディレクトリの実装](https://github.com/resonite-modding-group/ResoniteModLoader/blob/main/ResoniteModLoader/AssemblyLoader.cs)。

## 7. API

既存の認証と `{ok,data}`／`{ok:false,error:{code,message}}` を使用する。変更は同期応答とし、処理中の再操作は409で拒否する。

| メソッド・パス（`/api/v1` 以下） | 内容 |
|---|---|
| `GET /mods` | RML・Mod一覧、変更可能か、処理中かを返す |
| `GET /mods/releases?repo=...&page=1` | 公開リポジトリの正式リリースとDLL一覧（1ページ30件、次ページあり） |
| `POST /mods/check` | `{id}` の更新確認。`rml` は公式リポジトリ、その他は登録済み更新元 |
| `POST /mods/upload?name=...&id=...` | 本文をDLLとして追加。`id` 指定時はそのModの差し替え |
| `POST /mods/github` | `{id?,repo,tag,asset}` のDLLを追加／更新。`id:rml` は同じリリースのRML・Harmonyを取得 |
| `PATCH /mods/{id}` | `{enabled}` または `{repo,tag,asset}`（更新元の登録。導入版は変更しない） |
| `POST /mods/{id}/restore` | 前版へ戻す。復元後は前版なし |
| `DELETE /mods/{id}` | Modを削除 |

- Mod IDは新規登録時に生成する。RMLは固定ID `rml`。
- GitHub URLは `https://github.com/<owner>/<repo>`。取得時はGitHub APIで正式リリースと添付DLLを再確認する。
- 更新確認はGitHubのlatest正式リリースと記録済みタグを比較する。タグ不明は「導入版不明」と表示する。更新候補のasset名が前回と同名なら選択済みとし、それ以外は利用者が選ぶ。
- 主なエラー：400 `mod_invalid`、404 `mod_not_found`、409 `mod_busy`／`mod_conflict`、502 `mod_download_failed`、500 `mod_storage_failed`。確認失敗はUIに保持して表示する。

## 8. UI（2026-10-17 確認済み）

- 既存テーマ・部品に合わせ、上にRML欄、下にMod一覧を置く。各行に有効スイッチと更新確認。更新候補があるときに更新操作を表示する。
- 差し替え・GitHub更新元登録・復元・削除は行の「⋮」へまとめる。追加はDLLアップロード／GitHubの2ボタンと小さなダイアログを使う。
- DLL追加・差し替えダイアログは、ドロップ領域と「ファイルを選択」ボタンを使う（2026-10-18確認済み）。1ファイル・32 MiBまで。選択後にファイル名・サイズを表示し、「追加」／「適用」で送信する。選択とドロップは同じ検査を行い、不正な選択時はエラーを表示して送信不可にする。
- 稼働中は停止が必要な旨を表示し、変更操作を無効にする。狭い画面では操作を折り返す。

機能範囲の追加が必要になった場合は実装で補わず、先に相談して本書を更新する。
